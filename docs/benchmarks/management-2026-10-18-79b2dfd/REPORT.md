# 管理 API 默认配置性能基线分析

测试日期：2026-10-18（Asia/Shanghai）。被测提交：`79b2dfd3e043e946be2881c85a09dd0658b5e289`。

## 结论

**默认并发混合负载下，总体 FAIL，正式测量 3/5 轮通过。**
5 轮共 2000 次请求，按耗时加权吞吐 **43.52 req/s**，合并客户端延迟 **P95 412.816 ms、P99 626.810 ms**。
出现 **3 次 HTTP 503（0.15%）**，全部为提交工作流接口的 `database_busy`；服务并发过载计数为 0。

497 个入库工作流、994 个任务全部成功，结果正确、逐任务恰好一次执行、零重试、逐任务恰好一条 SUCCEEDED 事件。
另外 3 个提交返回 503 且未入库，故未达到预期的 500 个工作流/1000 个任务，不能将总体正确性判定为通过。
所有有效轮数据库完整性、外键校验和关闭检查均通过，协调器错误计数为 0。

独立的 3 轮数据库诊断均通过，但观察到本地写队列等待 P99 为 **1.98–3.13 秒**；
同轮 SQLite `BEGIN IMMEDIATE` P99 为 **5.42–7.02 ms**。
这支持本地写串行化队列存在明显等待的判断，不能据此把所有等待归因于 SQLite 文件锁。
诊断轮没有复现 503，因此尚不能把主测量的 3 次 busy 错误精确归属到本地写队列或 SQLite 锁获取的具体调用点。

## 被测版本、配置及统计口径

测试使用 `git archive HEAD` 导出的独立快照，未使用工作区未提交的业务修改。
本地 HEAD 和本地 `origin/master` 均为上述提交；连接 GitHub 失败，无法核验远端是否有更新。
版本、tree、原始差异哈希见 [provenance.json](provenance.json)，实际导入路径和逐源文件 SHA256 见
[主测量环境](baseline/environment.json)及[诊断环境](diagnostic/environment.json)。

环境：Python 3.12.10、SQLite 3.49.1、Windows 11 build 26200，22 个逻辑处理器。
CIM 硬件/内存信息在沙箱中不可读，没有专用机器或 CPU 绑定；结果代表该机器该次本地短批次抽样。

使用已有 `tools/benchmark_management.py`，每轮调用 **`run_benchmark()`，无负载/超时覆盖**：

| 项目 | 配置 |
| --- | --- |
| 工作流 | 100 个双节点 DAG：`root(abs(-i)) → join(identity(root))` |
| 混合读取 | 300 次：overview、分页 workflows、metrics 各 100 次 |
| HTTP 并发 / Worker | 8 / 4 |
| 基准工具设置的服务容量 / backlog | 16 / 32 |
| 完成轮询截止点 / 客户端请求上限 | 60 s / 10 s |
| 服务请求 / 管理读模型 busy timeout | 2 s / 2 s |
| 普通 SQLite 写连接超时 | 30 s；HTTP 写线程原有超时范围 2 s |
| Worker 轮询 / 心跳 / 协调器轮询 | 0.05 s / 1 s / 0.1 s |
| 主测量 | 1 轮预热 + 5 轮正式，每轮新库、新服务、新 Worker，顺序运行 |
| 锁诊断 | 另 3 轮相同默认负载，安装已有 `DatabaseProbe`，不计入主基线 |

HTTP 吞吐沿用工具口径：完成请求数（包括错误）/HTTP 批次耗时，批次计时包含 Worker 启动。
工作流吞吐包括 Worker 启动、HTTP 和完成轮询；初始化与关闭不计时。
客户端延迟包括成功及失败调用，分位数用 nearest-rank。
合并 P95/P99 从 2000 条原始延迟重算，**不是逐轮分位数的均值**。
完整协议、采集脚本的观测范围及复现命令见 [README.md](README.md)。

## 主测量结果

| 轮次 | 结果 | HTTP req/s | P95 ms | P99 ms | 最大 ms | 503 / DB busy | 完成工作流 | 任务尝试 | 完成耗时 s |

| 预热（不计汇总） | PASS | 44.62 | 344.294 | 521.905 | 1648.792 | 0 | 100 | 200 | 9.625 |
| 1 | FAIL | 37.13 | 518.999 | 564.773 | 2044.360 | 2 | 98 | 196 | 60.021 |
| 2 | PASS | 48.25 | 329.753 | 413.159 | 1869.447 | 0 | 100 | 200 | 8.909 |
| 3 | PASS | 43.52 | 350.297 | 626.810 | 2059.108 | 0 | 100 | 200 | 9.808 |
| 4 | FAIL | 42.81 | 408.597 | 495.607 | 2068.641 | 1 | 99 | 198 | 60.020 |
| 5 | PASS | 47.88 | 326.715 | 392.462 | 1293.447 | 0 | 100 | 200 | 8.958 |

正式轮 HTTP 批次耗时总和 45.953 s，2000/45.953 = 43.52 req/s；1997 次成功响应的吞吐约 43.46 req/s。
逐轮吞吐范围 37.13–48.25 req/s，中位数 43.52、样本标准差 4.526。
合并延迟 P50/P95/P99/max = **156.321 / 412.816 / 626.810 / 2068.641 ms**。

HTTP 状态：200 × 1500、202 × 497、503 × 3；没有客户端超时或其他 HTTP/网络错误。
500 次工作流提交中 3 次失败，提交接口失败率 **0.6%**；整体混合流量失败率为 0.15%。

正式轮完成耗时总和 147.716 s，原工具汇总工作流吞吐 **3.36 workflows/s**。
两个失败轮由于目标工作流数无法达到而一直等待默认 60 秒截止点，解释了该吞吐显著低于零错误轮的 10.20–11.22 workflows/s。
该数值包含基准的完成轮询语义，不能直接解释为执行器的稳态极限容量；失败轮未从汇总中剔除。

按原始请求提交顺序重建路由分组，各接口均 500 条样本：

| 接口 | 合并 P95 ms | 合并 P99 ms | 最大 ms | 错误 |
| --- | ---: | ---: | ---: | ---: |
| POST workflows | 553.643 | 1363.141 | 2068.641 | 3 × 503 |
| GET workflows?limit=10 | 171.905 | 190.804 | 236.006 | 0 |
| GET metrics | 220.814 | 258.168 | 274.497 | 0 |
| GET overview | 221.495 | 264.830 | 292.189 | 0 |

混合流量中读取占 75%，因此混合 P99 不能单独代表写入尾延迟；低比例 503 也不会直接出现在 P99 排位上。
原始逐请求延迟、每轮结果及完整原生日志均保留于 [baseline](baseline/)，原工具报告为 [suite.md](baseline/suite.md)。

## 数据库竞争诊断

| 诊断轮 | 写队列样本数 | 写队列 P95 ms | 写队列 P99 ms | 写队列最大 ms | BEGIN P99 ms | SQL execute P99 ms | busy/locked |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 593 | 357.244 | 2511.624 | 4013.686 | 6.608 | 21.810 | 0 |
| 2 | 599 | 350.205 | 3126.258 | 4616.507 | 7.015 | 22.249 | 0 |
| 3 | 592 | 320.207 | 1978.070 | 2559.319 | 5.416 | 20.752 | 0 |

探针的等待样本涵盖 HTTP、Worker 和协调器，**不是 HTTP 写入专属分位数**；Worker 等待适用原有较长超时，
所以这些分位数超过 2 秒不意味着相应 HTTP 请求必然失败。探针汇总覆盖服务创建后至关闭后的校验开始，详见协议。
`DatabaseProbe` 的直方图分位数为约 1% 分辨率的桶上界，与客户端原始样本的精确 nearest-rank 口径不同。
并发线程等待时长相加可以大于墙钟耗时，不能作为串行总运行时长解释。

3 轮共 1200 次请求、300 个工作流/600 个任务，零错误、零重试，全部正确。
诊断吞吐 44.95 req/s，合并 P95/P99 357.933/561.947 ms，工作流吞吐 10.55 workflows/s。
探针会改变调度和计时，且短批次本身存在波动，不能据此宣称性能改善或原有 503 已消失。
诊断结果和主测量分别保存；完整探针汇总见 [diagnostic](diagnostic/)。

主测量的 3 条 503 日志都明确标记 `failure_kind=database_busy`，
最终 `workflow_api_database_busy_total` 与 503 数一致，`workflow_api_overloads_total=0`。
这是数据库相关忙错误的直接证据。独立诊断显示较长等待集中于本地写队列，
但本次没有采到 503 当次的队列/SQL 调用点，因此“全部由本地写队列超时造成”仍是待验证假设。

## 执行正确性与失败范围

离线重新读取每轮 SQLite 备份，校验工作流 ID、精确节点集合、整数结果 `i`、SUCCESS、
`attempt_count=1`、`retry_count=0`、每任务 SUCCEEDED 事件数，以及 integrity_check/foreign_key_check。

第 1 轮缺少 `benchmark-98`、`benchmark-99`；第 4 轮缺少 `benchmark-99`。
其余 497 个工作流全部满足完整两节点执行与结果校验，未发现已接受任务重复执行、错误结果或半成品 DAG。
失败原因是预期提交/节点总数未满足以及完成截止点未达标，不能把原工具的 `single_attempts`、`task_results` 失败标记
直接解释为已存在任务执行多次或结果计算错误：该工具同时要求总数达到预期。

预热和诊断共另完成 400 个工作流/800 个任务，均通过同一离线复核。它们不计入主基线的 497/994 汇总。
完整逐轮复核、缺失 ID 与各项布尔结果保存在 [analysis.json](analysis.json)。

## 验证与可追溯性

在被测快照中运行现有基准验证与报告测试：7 + 7 = **14/14 通过**，日志为
[validation-tests.log](validation-tests.log)、[report-tests.log](report-tests.log)。
没有运行与本任务无关的全量业务回归；测试在全部测量结束后执行。

各轮保存原工具 JSON、400 条原始客户端延迟、逐任务结果、完整原生服务日志、最终 Prometheus 指标及 SQLite 备份。
采集时原生日志先存内存；数据库备份、导出和文件写入在原工具计时结束后进行。
除单列的诊断轮外，没有安装数据库探针。INFO 日志采集本身有少量观测开销，未做开销扣除。

首次采集因备份连接未显式关闭而在 Windows 临时库清理时报错，修正的是 `collect.py`；
随后发现沙箱以 WinError 10013 拒绝 loopback，400 次 URLError、服务端零请求。
这些环境/采集失败保留在单独目录，排除出应用性能汇总。正式数据在允许 loopback 的执行环境中重新完整采集。

本次采集未修改业务代码、业务测试及超时配置。最终审计发现主工作区在任务期间又发生了其他变动，
包括已有改动继续变化及另外两个文件出现修改，因此前后工作区 diff 哈希不相同；这些变化未进入隔离快照。
该事实记录在 [audit.json](audit.json)，不能声称整个共享工作区在测量期间保持静态。
主测量和诊断快照中的全部 35 个 src/tools Python 源文件均与各自运行前的哈希相同。
[SHA256SUMS.json](SHA256SUMS.json) 提供交付文件完整性清单；复现命令位于 [README.md](README.md)。

这是一份保留失败事实的当前提交本地基线。短批次、单机 SQLite 与内置简单任务不能代表长时间稳态、跨主机网络、真实模型推理或生产 SLO。
