# AI 工作流数据库竞争定位与优化（2026-10-17）

180 秒，两轮，每次独立预热 10 秒。北京时间 13:19 至 13:38 执行，与功能测试
分开运行；profile、阈值、benchmark 工具、Python/SQLite/平台及主机均未更换。

6 个正式轮次、6 个预热轮次和旧基线相对门禁全部 PASS。正式提交累计 18 分钟，

## 定位证据

优化前另执行 180 秒、8 并发的诊断负载，对 SQL 执行及连接租约入口/退出采样。
它有额外探针开销，仅用于定位，不作为容量对比基线。时间在多个线程间累计，
包含等待和调度，不能作为单线程 CPU 占比。

- TaskStore 连接租约约 34,909 次；当时每次租约均物理开关连接。入口累计约
  233 秒，退出约 50 秒，说明频繁连接准备/关闭是显著开销，而不只是单条慢 SQL。
- TaskStore 的本地 FIFO 与 WorkerRegistry 的直接 SQLite 写入各自竞争。
  初步连接复用后的独立短测中，1 并发 BEGIN P95 仍约 10.7 ms，尽管本地队列
  等待只有约 2.6 ms；说明等待被转移到 FIFO 外的心跳/注册写入。统一排队后的
  独立短测中，BEGIN P95 回到约 0.09 ms。正式长测再验证这一结果。
- 恢复协调器在持有写事务时执行
  `SELECT id FROM workflow_runs WHERE status!='SUCCESS' ORDER BY rowid`，查询计划
  为 `SCAN workflow_runs`。即使全部历史已成功、没有工作待协调，1 万条记录仍
  消耗约 30,010 条 SQLite 指令。它是确定的历史增长开销，但诊断中并非最大耗时，
  不能单独解释原先所有尾部波动。
- DAG 重复协调会更新未变化的节点/工作流状态，还构造调用者不使用的完整快照，
  额外读取节点、LLM 成功/失败事件和 token 统计，延长写事务并产生冗余写入。

LLM 用量的事件查询使用 workflow/task 索引定向访问，没有观察到随全局事件历史
线性扫描的执行计划。没有为此引入用量缓存或削弱预算的原子领取检查。

原始诊断见 [SQL 与连接采样](ai-sql-profile-before-2026-10-17.json)。
查询计划判读参考 [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)。

## 实现

1. `SQLiteTaskStore.connection_scope()` 为明确的后台消费线程提供有界连接复用。
   本地 Worker 和管理协调器各在线程内复用，退出即关闭；普通请求保留原先的
   独立连接生命周期。嵌套租约使用独立连接，每个租约结束时回滚未提交事务，
   防止读取快照延续至下一次操作；busy timeout 每次恢复，FULL 和外键约束保留。
2. 引擎创建的 WorkerRegistry 和任务写入共享同一本地 FIFO，避免心跳写入绕过
   写入排队。独立 registry 的默认行为不变，跨进程仍由 SQLite 事务互斥。
3. 为未成功工作流增加部分索引，先从索引读取少量未完成记录，再按 rowid 恢复
   原有处理顺序。没有直接强制指定索引，也没有漏掉 FAILED/PAUSED 状态。
   相同的空待办、1 万条成功历史查询由约 30,010 条指令降至 9 条。
   索引在首次打开既有数据库时自动建立。
4. 协调仅在状态/错误实际变化时写入；恢复轮询使用不构造返回快照的内部路径。
   公开的 submit/advance/get 仍返回完整节点和用量快照；预算检查仍在领取事务内。

RemoteTaskStore 明确提供无操作的 connection scope，远程 Worker 不打开 SQLite。
Worker 的异常和停止清理覆盖 scope 的进入/退出，确保心跳线程停止并正确确认排空。

主要源码为 persistence.py、worker_registry.py、workflow_store.py、recovery.py、
reliable_worker.py、management.py、remote.py。测量基于 Git HEAD `c5534d0`，以上
优化与新增测试/报告尚未提交。benchmark 工具及原基线未改变。

## 原末段问题的复测

窗口均按工作流开始时刻归组，包含最终在途排空。以下比较完整首/末 30 秒窗口。

| 8 并发 | 首窗 → 末窗工作流数 | 首/末窗工作流 P95 ms | 首/末窗 writer P95 ms |
| --- | --- | --- | --- |
| 优化前轮 1 | 483 → 273（下降 43.5%） | 655.5 / 1512.0 | 68.5 / 171.1 |
| 优化前轮 2 | 468 → 386（下降 17.5%） | 682.1 / 901.3 | 68.5 / 89.6 |
| 优化后轮 1 | 601 → 551（下降 8.3%） | 581.7 / 587.5 | 46.9 / 49.8 |
| 优化后轮 2 | 442 → 648（增长 46.6%） | 956.7 / 481.5 | 91.4 / 31.8 |

本次未重现原先 17%–43% 的末段下降。优化后第二轮首窗偏慢，不能把后续回升
解释为持续加速。结果支持已修复路径有明显收益，但未逐项做性能消融，也未隔离
全部磁盘/系统调度因素，不能承诺所有运行波动都已消除。
模型仍为本机固定延迟 HTTP 模拟；每个独立数据库连续测量 3 分钟，本次不是
数小时单库稳定性或真实模型推理测试。

## 回归保障和复现

新增 14 项测试：连接线程隔离、嵌套租约、异常关闭、快照释放、未提交事务回滚、
超时恢复、远端无数据库、scope 失败的心跳清理、注册写入不可绕过 FIFO，以及
历史规模的 SQLite 指令数、重复协调无写入、无用快照、旧库索引升级与顺序。
历史成本门禁通过 SQLite 指令计数判断，不依赖墙钟速度；新增 5000 条成功历史
不能让同一协调轮次额外增长超过 1000 条指令。旧实现该用例约增加 15,000 条。

最终完整回归：**480 passed, 4 skipped，95.84 秒**。
